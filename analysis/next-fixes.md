## 1. Update-copy failure handling

**User benefit:** an interrupted or failed update should retain enough information and files to recover, rather than report progress and discard its source.

The existing [recovery investigation](updater-recovery-contracts.md) shows that `UpgradeManager.exe` copies staged files without checking CopyFileW success, can delete the source afterward and performs unconditional staging cleanup higher up. Version publication can also precede completed copying. This is the most valuable reliability work before another release, but needs a coordinated recovery design, not a single delete guard.

Completed development scope: checked copy/readback, recursive error propagation and exit before caller cleanup, retained staging/backup, version last, English image-independent errors and a recovery pause for ambiguous checkpoints. 93 written-byte fixture cases pass, including every previous-release path with representative bytes. Remaining work: native CE loader/storage/display tests, durable manifests/commit, real partition-mount verification, controlled obsolete-file/backup cleanup and original OS/MCU/formatter error paths. This is not an established repair for GitHub #7/#15.

## 2. Touch release that leaves a hold active

**User benefit:** a held button should stop when the finger is lifted, including outside the button.

The [interaction investigation](appmain-interaction-contracts.md) and re-read original `13e620` show that an outside release can clear pressed-state without clearing selection or timers. A subsequent hold/repeat event can still dispatch. USB seek buttons use this machinery. The necessary outside-up-without-move event order has not been observed on the actual touchscreen.

Implemented in development: the actual release calls the existing cancel routine before pressed-state is cleared. 117 byte-interpreter checks include queued timers, inclusive edges, normal gestures and actual USB seek-stop IPC. Native touch-event ordering and lifetime/reentrancy still need checking; see [implementation](media-responsiveness-development.md).

## 3. USB music resume after adding files

**User benefit:** return to the same song and position after editing an otherwise unchanged USB stick.

The [USB resume investigation](usb-media-input-contracts.md) shows that resumePlay checks exact free space as well as volume/file identity. Adding another file changes free space and can reject resume even if the saved track is unchanged. This behavior is established in the code; no corresponding unit incident is claimed.

Implemented in development: only free-byte equality is bypassed; saved path, size/serial, total capacity, API success and graph-load checks remain. 25 actual-byte resume/rematch checks cover changed libraries and identity/load failures. Native scan/restart/audio-focus behavior still needs checking; see [implementation](media-responsiveness-development.md).
