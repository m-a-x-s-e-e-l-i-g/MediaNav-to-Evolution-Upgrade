# AppMain startup failure handling

The complete [development payload](../build/startup-failure-development-01/README.md) retains every one of the 1,918 files and earlier improvements from shared-mapping-development-01. Only AppMain changes. No LGU, version bump or release is created.

## Observed defect and resulting behavior

AppMain constructs its shared-memory object during CRT static initialization, before WinMain. The function at `140fb8` allocates 312 bytes and calls the mapping initializer at `14111c`, but previously discarded its Boolean result. Even after a failed mapping it continued registry reads and published the partially initialized object through `186308` and `186ce8`. Returning NULL alone would still allow the subsequent static constructors to run.

The new check stops that sequence when initialization fails. It clears both publication/cache globals, attempts to unmap and close each acquired view/handle, releases the allocated object once and calls the existing `TerminateProcess` import for the current AppMain process. Failed cleanup does not prevent cleanup of remaining resources; retained resources are left for process teardown. If termination unexpectedly returns, the code sleeps for one second and retries termination without continuing initialization or freeing the object again.

Allocation failure follows the same stopping policy without accessing a NULL object and displays an English startup error. Mapping failure keeps the existing warning. Successful initialization and the cached-object path retain their original behavior. This does not implement automatic restart, unit reboot, or a recovery screen after AppMain exits.

## Binary scope

- Input AppMain SHA256: `1ff9fd6c5d4029745182da69af453eef43d27b94565ca3fa567021055a49c589`.
- Output AppMain SHA256: `935dabf375402934109a69611860985048d21b0b7c56a1cf1f3533cf1f8eb3c8`.
- Original code changes only at `14111c` (4 bytes) and `1411b0..1411c4` (20 bytes). A new 4,096-byte read/execute `.mxboot` section holds the check, cleanup/stop routine and constant text. File size grows from 1,756,160 to 1,760,256 bytes.
- Existing imports, entry point, resources, data and original section headers remain intact. All original exception rows keep their positions; two helper rows and corresponding relocations are added. The recipe reverses every change in the original file prefix back to the exact input.
- `TerminateProcess(0x42, 1)` uses the same existing pseudo process handle as the original CRT termination code. No new imports, registry/file writes or MCU commands are added.

## Validation and limits

The actual entry sequence, static-initializer table traversal, memory constructor and mapping initializer execute in the MIPS byte interpreter. The other static constructors, GUI, allocation, mapping, registry and process APIs use explicit fixtures. Firmware is never executed as a native Windows program.

157 behavior cases plus one structural check cover all 14 mapping creations and views failing, allocation failure, healthy/cached parity, partial cleanup failures and unexpected termination returns. Failure paths stop before the remaining 59 static constructors and GUI. Preferred address and three aligned alternate load bases are checked. Healthy-object comparisons account for its rebased vtable pointer.

Retained checks on the written AppMain include 124 mapping cases, 96 relocated copy/text cases, 1,872 separate relocation instruction checks, 96 IPC/retry cases, 824 Bluetooth pairing/UI cases, 117 touch/seek cases, 140 Hebrew mixed-text cases and 172 Arabic mixed-text cases, plus existing NULL/benchmark checks. MgrUSB is exactly unchanged; its prior 72,497-case proof and nine notification-state cases are carried forward and were not rerun.

Native CE loading, exception unwinding, OS process teardown and the unit's behavior after an early AppMain exit remain unverified. The change prevents the demonstrated continuation into incomplete initialization; it does not establish successful system recovery or a fix for the update-screen reports in GitHub issues 7 and 15.

The manifest pins the new build tools, proof, previous manifest and every payload member. Existing staging, tools and proofs are preserved. The published MAX03 LGU and guide are unchanged.

## Continuing USB snapshot investigation

The [additional five-case reader audit](firmware/usb-status-reader-audit.json), generated by [audit_usb_status_readers.py](../tools/audit_usb_status_readers.py), tests actual reader instructions on this AppMain hash. A title without a terminator in its 260-WCHAR slot is read into the adjacent artist field. A fixture publication between the cover handle's `LWL` and `LWR` produces a mixed handle belonging to neither status. The widget helper stores the borrowed handle at `+3c` and queries it through GetObject; it does not duplicate the bitmap in this routine.

These are controlled input/interleaving reproductions, not observations of the native scheduler or a complete GDI ownership analysis. The full status writer still copies without reader coordination. Coherent snapshots must cover text/scalar readers, notification order and handle lifetime; copying the structure once cannot by itself keep a subsequently retained bitmap alive. No shared-status concurrency fix is introduced in this build. Bound the text consumer, then follow cover replacement/deletion and widget drawing before choosing a coordinated publication design.
