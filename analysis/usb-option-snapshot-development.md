# Consistent USB repeat and shuffle selections

The USB options screen read repeat four times and shuffle twice during one refresh. A status publication between those reads could leave two repeat choices selected, or no choice selected. Shuffle could similarly show both on and off, or neither. The [previous scalar-reader audit](firmware/usb-scalar-readers-audit.json) reproduced those outcomes using the original reader instructions and simulated publication.

This development uses **one coherent eight-byte snapshot of repeat and shuffle per refresh**. The existing nonblocking named-mutex copy helper copies `MAP + 0xe42..0xe49` into a private stack buffer. It releases the lock before the menu updates its six selection flags. The existing predicates are preserved, including full-DWORD comparisons and conditional writes only when a selection actually changes.

If the mutex is busy, creation/wait fails, or the object/mapping is NULL, the repeat/shuffle choices retain their current values. The completion marker at object `+0x7c` also retains its current value. After a successful refresh, the original transition from `2` to `3` remains; other values stay unchanged. A later successful invocation on the same initialized dialog updates the choices correctly. This does not establish when the native application will schedule that next invocation.

The original initializer entry `4f754`, 40-byte stack frame, prolog, epilogue and virtual-method pointer are preserved. Earlier theme, label, registration, USB-icon and redraw calls retain their order. These calls occur before acquiring the snapshot lock. The new helper has its own 64-byte frame and 16-byte prolog. It occupies existing zero padding at `1c6200`, uses 280 bytes, and adds one exception row. No new sections or imports are needed. Active exception/relocation tables remain at their previous locations and grow within existing padding; the section layout and image size stay unchanged.

The complete [development payload](../build/usb-option-snapshot-development-01/README.md) starts from USB snapshot copy development-02 and retains **all 1,918 previous files and fixes**. Only AppMain changes. MgrUSB, the other 1,917 files and the optimized COPY helper bytes remain unchanged. There is no LGU, version bump, release or GitHub publication.

## Validation

The verifier interprets the complete initializer entry, prolog, modified body, new helper and original epilogue at the preferred image base and three aligned alternate bases. It checks all eight valid repeat/shuffle combinations against the previous initializer, ten different initial selection patterns, both language/USB-icon paths, invalid full-DWORD predicate parity, unchanged completion states, NULL/create/wait failures, abandoned-lock success and a busy-then-success refresh of the same dialog.

All 64 old/new pairs of valid settings are tested with publication before lock acquisition, during the copy, after the snapshot, and during the selection writes. Publication during the copy is explicitly deferred until unlock. The resulting six flags always describe one complete pair. Shared reads stay within the eight-byte range; selection and completion writes occur after unlocking. Unchanged choices retain the original no-redundant-write behavior. Stack and callee-saved registers are checked with caller-clobbering API fixtures.

The declared edit recipe reverses exactly to the previous executable. Existing exception rows and relocation records outside the replaced body stay intact; the helper row and hook/helper references are checked after rebasing. The original virtual-method pointer still targets `4f754`.

Complete title/artist/cover consumers, original cover callers and AppMain startup/mapping/IPC/Bluetooth/touch/text checks rerun on the written payload. MgrUSB is byte-identical, so its prior hash-pinned regression evidence is carried rather than rerun. COPY code, its exception row and its relocation records are unchanged; its previous exhaustive proof is retained, while the complete text consumers exercise it again at four image bases. Counts and hashes are recorded in [the proof](firmware/usb-option-snapshot-development.json) and the build manifest.

All **1,411 new checks** passed: 1,410 behavioral cases, including six original defect reproductions, and one structural check. **375 retained text/cover consumer checks**, **32 original-caller checks** and the retained AppMain regressions also passed. AppMain remains 2,010,112 bytes; SHA-256 is `53dad71c39ec89fcc3cda17825eb48b8ce67b23563ab50c51f9fb77279acb835`. The three new build/patch/verification tools, proof, prior manifest and all member hashes are pinned in the manifest. Original tools/proofs/builds remain intact.

Mutex operations, publication scheduling and earlier UI subfunctions use fixtures. Firmware is **not executed natively**. Native CE loading/unwind, GUI scheduling, rendering and unit behavior still require testing. The six other direct playback-status readers and producer-side local metadata construction remain outside this fix; this is not a claim of general shared-status atomicity or a native performance measurement.
